# 知返的并发设计：从一次上传回执丢失讲起

知返可以用来讨论多实例幂等、过载保护和故障恢复。最容易举证的是分片上传：两个实例收到同一批重传，本地隔离实验中，对象存储的逻辑写入量由 60 MiB 降到 5 MiB。生产环境可承诺的视频完成速率、问答 P99 和同时在线人数仍待测量。

## 面试开场（约 90 秒）

> 知返把课程视频和 Markdown 放进同一个能追问、能复习的资料库。一个用户上传大文件时，另一个用户可能正在等一句带出处的回答。我分别看上传消耗多少存储带宽、交互请求排多久，以及视频从入队到发布要多久。
>
> 举个我实际复现的问题：服务端已经写好分片，客户端没收到成功回执，便把同一块再传一次。原先每次重传都会覆盖 MinIO 的同名对象，文件最终正确，额外的带宽很容易被忽略。我保留上传会话的行锁，先校验用户、分片长度和清单里的 SHA-256，再读 MySQL 的分片回执。已有回执就直接确认。两台 Spring 实例同时接 12 份相同的 5 MiB 分片，改动前有 12 个对象版本，改动后只有 1 个。我还故意让数据库在对象写完后报错，确认另一个实例可以重写同一个键并补回执。
>
> 这个改动省下了重复写入的 55 MiB。客户端仍传了 60 MiB，首写仍会持有数据库行锁。如果要给出生产承诺，我会先测重传比例、锁等待和连接池占用，再决定是否值得让客户端直传对象存储。

## 哪些大厂实践适合这里

- **Amazon 的幂等 API。** 创建资源后，客户端可能收不到响应。Amazon 用调用方表达的唯一请求标识识别重试，并比较参数，以防同一标识被用于不同意图。知返已有“账号归属、上传会话、分片序号”和不可变哈希清单，可以直接据此判定。两个序号即便内容相同也分别确认。分片用 MinIO 的普通对象 PUT 保存，数据库回执提交后才允许跳过后续存储写。[Amazon Builders’ Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-apis/) · [上传实现](../platform/src/main/java/org/videoparse/UploadService.java)
- **Netflix 的交互与批处理隔离。** Netflix 的 concurrency-limits 项目演示了 live 和 batch 流量共享服务时怎样预留执行容量，也给出了随延迟调整并发上限的算法。知返有确定数量的 Python worker，采用固定执行位和有上限的等候位。两个 worker 时，下载最多占一个，另一个可以处理问答。仅有下载时会损失一部分吞吐。只有一个 worker 时，两类请求仍会争抢同一位置。[Netflix concurrency-limits](https://github.com/Netflix/concurrency-limits) · [worker 准入](../platform/src/main/java/org/videoparse/StudyTools.java)
- **阿里 Sentinel 与 Google SRE 的过载案例。** Sentinel 在双十一的突发流量和慢下游场景中分别使用流控、削峰和熔断。Google 的经验是请求成本差异大时，单一 QPS 指标容易误导，连拒绝请求本身也有成本。知返的 429 放在创建媒体进程和调用模型之前。本次隔离复测用两个被占满的 worker 接 24 个额外请求，22 个在 1 秒内拒绝，拒绝耗时 P50 为 11 ms、P95 为 3011 ms；排进两个等候位的请求可以一直等到 3 秒。这里验证了应用的准入策略，模型供应商由替身控制。[阿里 Sentinel](https://github.com/alibaba/Sentinel) · [Google SRE《Handling Overload》](https://sre.google/sre-book/handling-overload/) · [复测程序](../platform/checks/worker_admission.py)

## 上传实验如何复现

在本机隔离环境中使用两个 Spring JVM、MySQL 8.4、Redis 和启用版本控制的 MinIO 测试桶。用屏障同时发起 12 个 HTTP PUT，轮流发给两台实例，使用相同账号、会话、序号和内容。两组运行的业务代码仅上传服务实现不同。用该分片对象键的已写版本数计算逻辑写入量；压缩、复制和物理磁盘写放大未计入。

- **同一分片。** 两组各有 12 个请求成功。原实现产生 12 个版本，改后产生 1 个。客户端上传量、摘要计算次数均保持 12 份。
- **两个不同序号。** 两份内容完全相同，两个序号各写入一个版本，合并成功。重复完成返回原视频 ID。
- **回执写失败。** 用仅匹配本次上传 ID 的 MySQL 触发器中断分片回执插入。客户端收到 500，查询已确认分片为空，MinIO 已有一个版本。移除故障后从另一实例重传，产生第二个版本和一条已提交回执。该窗口允许重写。
- **错误请求与过期。** 开放会话中，错误摘要返回 400，另一账号尝试重传返回 404；两者都未产生新版本。正确重传会刷新开放会话的过期时间。新实现对已完成会话仍验证清单，合法迟到请求成功，错误内容返回 400。

复测需要空闲的测试库、两台共享 MySQL/Redis/MinIO 的实例、一个已启用版本控制的测试桶，关闭上传口令，HTTP 本地测试设 `SESSION_COOKIE_SECURE=false`。测试账号通过 HTTP 注册，数据库连接需要创建和删除测试触发器的权限。Python 环境需安装 `requests`、`sqlalchemy`、`pymysql` 和测试用的 `minio`。设置 `UPLOAD_TEST_DATABASE_URL`、`MINIO_ENDPOINT`、`MINIO_ACCESS_KEY`、`MINIO_SECRET_KEY`、`MINIO_BUCKET`，然后执行下列命令。脚本会留下测试账号和版本对象，实验结束后可销毁整套隔离环境。[完整检查](../platform/checks/upload_retries.py)

```bash
python platform/checks/upload_retries.py http://127.0.0.1:9090 --peer http://127.0.0.1:9091
```

要做前后对照，可用 Git 历史中本次改动前的 `UploadService.java` 构建另一组实例，对原实现运行同一命令并加 `--baseline`。

## 面试官继续追问时

**“加了唯一键，为什么还需要应用层处理？”** 唯一键一直都在，约束的是 MySQL 里的回执行数。旧实现先写 MinIO，之后才处理重复键，两个并发请求仍可能产生两次存储写。现在在同一上传会话的行锁内读已提交回执，对开放会话仍先核对内容。这多付出一次主键查询，同一文件的不同分片仍会串行，独立上传会话各自锁自己的行。

**“为什么不把慢 I/O 移出事务？”** 如果把 PUT 直接挪走，过期清理可能先删掉会话，晚到的写入又留下孤儿对象。当前行锁把写分片、完成和清理排好顺序。若代表性负载下锁等待和连接池等待已吃掉上传时延预算，下一步比较预签名直传和当前方案；前者还要设计对象校验、完成确认与过期清理的竞争协议。

**“发件箱是不是能保证任务只执行一次？”** 创建任务与发送意图在同一 MySQL 事务提交。多个发送方用短事务领取到期记录，释放行锁后再发 MQ，按租约确认。两名发送方对 8 条意图实测发送 8 次。若 broker 已收消息而发送方在确认前退出，租约到期还会重投。消费者重查任务阶段与执行锁，外部模型调用到检查点落盘之间仍可能重做。[发送方](../platform/src/main/java/org/videoparse/DispatchOutbox.java) · [故障检查](../platform/checks/DispatchOutboxCheck.java)

**“Redis 丢通知、用户断线、两个账号问同一句话，各会怎样？”** Redis 只用任务 ID 唤醒订阅者，进度事件及游标在 MySQL，浏览器用 `Last-Event-ID` 接着读。查询向量缓存按账号、模型空间和完整问题区分，命中后仍需根据资料归属和内容版本检索。共享层冷启动时两个 JVM 仍可能各调用一次嵌入模型。[事件流](../platform/src/main/java/org/videoparse/TaskEventStreams.java) · [检索与缓存边界](retrieval-storage-decision.md)

**“如果流量翻十倍，能否给我一个数字？”** 先请面试官指定流量构成和用户体验目标。对上传记录文件大小、重传率、对象写入量和锁等待；对解析记录视频时长分布、供应商配额、每分钟完成数和队列最老任务年龄；对问答记录到达率、成功响应 P99、排队耗时和 429 占比；对 SSE 单独测活跃连接数、事件新鲜度和重连补读量。逐级升压后保持负载并观察积压能否消退，再报告满足约定指标的区间。增加平台实例还会放大对共享 MySQL 和模型配额的竞争。[现有隔离实验与部署边界](platform-migration.md#并发容量与实测)
